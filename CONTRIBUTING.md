# Contributing

Start with `docs/STATUS.md`, `results/theorem_index.md` and the exact source of the branch you want to study. Coordinate the statement and scope in an issue before overlapping proof work. Small thematic pull requests are preferred: one theorem, one formal bridge, one checker, or one literature audit.

Create a branch from `main`: `proof/topic`, `formal/topic`, `compute/topic`, `literature/topic`, or `fix/topic`. Commit sources and unique certificates, not caches or regenerated binaries. Open a PR with the supplied template; another researcher should review substantial mathematical changes. Repository protection requests passing core/formal CI, but allows solo maintenance with zero required reviewer approvals. Never force-push shared main or rewrite historical identity records. No collaborator is added automatically.

Name new proof notes `proofs/paper/descriptive_name.md`, new Lean units `formal/lean/DescriptiveName.lean`, and new computational modules `computations/src/descriptive_name.py` (C++ likewise). Existing compatibility paths keep their original names. Use unique qualified Lean namespaces; list new accepted modules in `formal/modules.json`, and regenerate/review the exact inventory only after a successful kernel run. Frozen OpenMath inventory files do not acquire new declarations.

Every important result receives a stable ID and exactly one status: FORMALLY VERIFIED, PROVED ON PAPER, COMPUTATIONALLY VERIFIED, CONJECTURED, REFUTED / NEGATIVE RESULT, or EXPLORATORY. Split paper theorems, finite controls and formal bridges into separate entries rather than assigning multiple statuses. Update `results/result_index.json` and its Markdown index with the exact hypotheses/domain, source, proof/check outcome, dependencies, and priority status. Never infer an all-n theorem from finite checks. Priority defaults to OPEN until supported by a documented literature audit. A source document may contain several differently classified results; its catalog entry is only an EXPLORATORY navigation record, not a blanket claim about its contents.

Document original-letter cost, word order, image-versus-subset distinctions, and coverage completeness. Record seeds, arguments, raw inputs, exact witnesses/cuts and rejection controls. Put fresh experiment output under `.reproduction/` until reviewed. Large unique datasets should become versioned release assets with hashes and a hydration manifest. Document any redaction or exclusion; preserve immutable originals separately.

Run `python scripts/reproduce.py --suite all` before submitting accepted proof/code changes, plus the relevant independent checker. Explain which expensive checks you ran or intentionally deferred. For proof-only notes, do not claim CI certifies the paper argument. Preserve baseline, post-baseline, OpenMath packaging and collaborative contributions separately, including AI/tool assistance. Report counterexamples as exact transition rows and a reproducible check.

The imported-source manifest retains immutable original hashes and checked public-copy hashes. If you intentionally change an inherited file, preserve its original hash/stage, document the new public revision and update its public hash after review. Stage changed/new files, then run `python scripts/seal_public.py` to refresh the publication seal (which excludes only itself), stage the seal, and run core checks. Do not treat an original historical seal as a seal of new collaborative content.
